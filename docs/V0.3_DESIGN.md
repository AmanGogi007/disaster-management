# V0.3 — Dam-Break Hydraulic Simulation: Architecture Design (DESIGN ONLY)

> **Status: design document — NOT yet implemented.**
> This proposes the architecture for V0.3 on top of the working V0.2 system.
> It exists so we agree on the model, its physics, its honest limits, and the
> build order *before* any simulator code is written.
>
> V0.2 already gives us: real OSM water geometry, plot attachment,
> upstream/downstream tracing, main-stem vs tributary classification,
> dam/reservoir relationships, DEM-based attachment methodology, 48/48 tests,
> and a verified real-world Sutlej/Punjab case.

---

## 0. What the user/property wants answered

The engine is ultimately a **Property Hazard Engine**, not a dam-break simulator.
Dam-break / dam-release flooding is **Scenario #1** of several hazards that will
eventually share the same geometry and risk plumbing:

```
                  PROPERTY
        ┌────────────┼────────────┐
        ↓            ↓            ↓
     FLOOD       EARTHQUAKE    EXTREME RAIN (LATER)
        ↓            ↓
   river flood   dam/breach  <- V0.3 starts HERE
        ↓
      DEM + hydraulic solver
        ↓
     depth · velocity · arrival · inundation · duration
        ↓
      RISK ENGINE  →  PROPERTY REPORT
```

So V0.3 builds the **hydraulic hazard engine** as *one modular hazard*, with the
risk/reporting layer kept generic so a later earthquake/rain hazard slots in
beside it. We rework V0.2's plumbing (provenance, confidence, reports) but do
**not** rewrite V0.2 itself.

For the flood hazard specifically, the question is:

> “If the upstream dam (e.g. Bhakra) fails or releases a given amount of water,
> how deep / how fast / how soon does water reach my plot?”

A defensible answer has **five outputs**, each with provenance and uncertainty:

| Output | Unit | Concrete V0.3 target |
|---|---|---|
| Flood **arrival time** at plot | hours/min after breach | `t_arrival_h` |
| Max **depth** at plot | m | `max_depth_m` |
| Max **velocity** at plot | m/s | `max_vel_mps` |
| **Peak discharge** at dam / along path | m³/s | `peak_q_cms` |
| **Inundation extent** + **duration** | km² / hours | raster + `duration_h` |

V0.3 must **not** present these as exact predictions. They are the output of a
*model* driven by assumptions; every number carries a confidence band.

## 1. DEM / terrain data source & resolution

**Reality check first:** today `ELEVATION_PROVIDER=sample` returns a *synthetic*
landscape (`SampleProvider`, `packages/geo/terrain/provider.py`) and is
**explicitly not survey data**. A flood model computed on the sample DEM is
meaningless for real decision-making. So V0.3's first **hard dependency** is a
real DEM provider.

Recommended priority (from `docs/DATA_SOURCES.md`, already authored):

1. **Copernicus DEM GLO-30** (30 m, Copernicus licence) — primary. Global,
   void-filled, best available free terrain.
2. **SRTM GL1** via OpenTopography (30 m, public domain, needs API key) —
   fallback for regions not covered or as cross-check.
3. **Bhuvan / CartoDEM (30 m)** — India-specific, NRSC terms. Use if the
   flood zone is India-centric and a higher trust source is wanted.

Resolution guidance — **two numbers, always reported separately**:

- `source_resolution` = native resolution of the acquired product (e.g. **30 m**).
- `simulation_grid` = resolution of the working raster (e.g. 10–30 m).

**Never imply that resampling a 30 m source to a 10 m grid creates 10 m terrain
information.** It creates 10 m *cells* containing ~30 m information. The report
must distinguish these explicitly.

Also note Candi's honest framing: **Copernicus GLO-30 is a DSM, not a bare-earth
engineering survey.** Its published absolute vertical accuracy is < 4 m at 90%
linear error. It cannot see the riverbed or narrow structures (see §B on the
channel problem); treat it as the *starting* terrain, not the truth.

Use **drainage-conditioning** (pit filling / breaching) for the *classic*
flow-direction analysis. For flood *extent* we use HAND as a prior only — see §9.

### Vertical datum — mandatory metadata

This is a correctness issue, not a nicety:

- **Copernicus GLO-30 is referenced to EGM2008** (geoid). Indian
  CWC/India-WRIS/BBMB gauge and reservoir elevations may be referenced to a
  different local datum (e.g. a national datum or MSL).
- These are **not directly comparable** until transformed to a common reference.

Therefore **every** terrain and hydraulic dataset must carry explicit metadata:

```
horizontal_crs:   EPSG:4326 (or projected EPSG for the working grid)
vertical_datum:   "EGM2008" | "MSL" | "national-datum" | "unknown"
vertical_offset_m: float | null   # applied offset vs a declared reference
```

Before comparing a DEM elevation with a dam/gauge elevation we MUST:

1. Read both datums,
2. If they differ, apply the geoid/datum offset (or explicitly reject the
   comparison as `confidence=low` / `not-for-decision`),
3. Tag every number with the datum it is expressed in.

**Phase 0 must resolve the Bhakra–Ropar datum situation on real data** (see §I).

## 2. Terrain pre-processing pipeline

Runs once per analysis footprint, cached (§17):

1. **Acquire** real DEM (Copernicus/SRTM) for the corridor bbox.
2. **Resample** to working resolution (10–30 m) → new `DEM`.
3. **Fill sinks / breaching** → `filled` DEM (needed so D8 flow actually
   reaches the dam's downstream).
4. **Slope** − % or degrees grid.
5. **Flow direction** (D8) — already exists:
   `d8_flow_direction` (`packages/geo/watershed/flow.py`), keep.
6. **Flow accumulation** — already exists:
   `flow_accumulation`, keep (`packages/geo/watershed/flow.py`).
7. **Watershed / catchment** of the dam — new: the contributing area of the
   chosen upstream dam, to define the inflow hydrograph (§6).
8. **HAND** (height above nearest drainage that is *network-connected*) — new;
   the basis of depth mapping in §9.

All pre-processing outputs are **derived GIS data** (not measured), and must be
flagged as such in provenance. Each derived raster inherits the source DEM's
`horizontal_crs` and `vertical_datum` metadata.

The existing `DEM` + `AffineTransform` model (`packages/geo/raster/dem.py`)
should be **kept and extended** (add `source_resolution_m`, `simulation_grid_m`,
`horizontal_crs`, `vertical_datum`, `vertical_offset_m`, and a warp/resample
helper), not replaced.

## 3. Integration of the OSM river network with terrain

**The single most important architectural correction:** the OSM river network
(and its `downstream_trace`) defines where water is *hydraulically connected to
the downstream system* — i.e. the **source and the channel** — but it is **NOT
the complete flood propagation path.**

Once water over-tops or breaches the channel, the water body is free to spread
across whatever hydraulically connected cells the terrain permits, **including
areas with no OSM waterway at all** (fields, villages, roads, depressions):

```
                  RIVER  ════════════════════════
                      ↓
                 flood wave
              ↙        ↓        ↘
         field      village      road
            ↓          ↓           ↓
        lowland      basin      depression
```

So the roles are:

- **OSM network + `downstream_trace`:** determines the hydraulic *source* and
  the *river/channel* where the flood wave is introduced. It tells us *where*
  water enters the downstream system, and the reach along which the dam's wave
  travels in-channel.
- **DEM + hydraulic solver:** determines where the water *actually goes once it
  leaves the channel*. The solver propagates over **hydraulically connected
  floodplain cells regardless of whether an OSM waterway exists there.**

Concretely:

1. Trace the downstream reach from the dam to the plot (`downstream_trace`) to
   establish **connectivity = “the plot is in the dam's hydraulic system.”**
2. Introduce the flood wave at the dam / the traced channel.
3. Let the **2D shallow-water solver** route it over the DEM floodplain; the
   plotted area floods iff the solver says the water reaches it — **not** iff the
   OSM graph happens to have an edge there (and not only within the river graph
   either).

To align the DEM with the OSM channel axis (so flow follows the same river the
network uses), we **burn the OSM polyline geometry into the DEM** as an
elevation hint. This is an *aid to routing*, **not** a substitute for real
bathymetry (see §B).

## 4. Dam / reservoir data model

V0.2 treats dams as `NetworkFeatureLink` + `WaterFeature` (name, lat/lon,
type, distance, relationship). V0.3 needs a **dam characteristics record**,
still attached to the same network node. Proposed (all fields nullable, each
tagged `source` = otl | gis | assumption):

```
DamRecord:
  id, name, lat, lon
  network_node_id            # from V0.2, into downstream_trace path
  height_m                   # crest height
  storage_m3                 # total reservoir capacity
  normal_pool_elev_m         # normal retention level
  max_pool_elev_m            # top of dam / flood control level
  dam_type                   # gravity | embankment | arch | rockfill
  length_m                   # crest length
  outlet_capacity_m3s        # if known (spillways, sluices)
  elevation_of_thalweg_m     # river bed at dam toe  -> needed to compute flood depth
  # new: every elevation field carries a vertical datum tag
  vertical_datum             # "EGM2008" | "MSL" | "national-datum" | "unknown"
  vertical_offset_m          # applied offset vs declared reference (see §1)
  source: str                # data source / provenance tag
  confidence: "high|medium|low"
```

**Sources (honest):**
- **Measured / observed (high trust):** India-WRIS / CWC dam registers, Bhakra
  Beas Management Board (BBMB) published specs — *real numbers, cited*.
- **Derived GIS (medium):** crest/storage from published sources; dam footprint
  from OSM; thalweg from a real DEM (not the sample).
- **Assumption (low):** anything we must fill because a number is proprietary
  — must be explicit (`assumption: true`).

Missing fields must cause *graceful degradation* (fewer outputs, wider
uncertainty), **never** silent fabrication.

## 5. Dam-break scenario model

A scenario is the *boundary condition* we push into the hydraulics. Proposed
enumeration (each reusable, storable in `simulations/scenarios/` — dir already
exists):

```
BreachScenario:
  scenario_id, label
  breach_kind: "instantaneous_piping" | "overtopping_progressive"
  breach_width_m, breach_depth_m, breach_slope, breach_formation_time_h
  initial_reservoir_stage: "normal_pool" | "max_pool" | "custom_m"
  inflow_series: optional rainfall-driven inflow (V0.4+)
```

Deliberately **V0.3 starts with a small, well-understood set**, not a generic
flood simulator:

1. **Simplified breach** of an upstream dam/reservoir (worst-case partial
   breach), producing a downstream hydrograph.
2. **A specified release** (“what if X m³/s for Y h”) for weirs/diversions
   (e.g. Ropar Headworks, which V0.2 saw downstream) that have no breach but
   can *release* water.

This keeps us honest: Ropar is a diversion headwork (release), **it is not a
dam that breaches** — the system must know the difference.

## 6. Breach parameters & assumptions

The physically crucial inputs and our default assumptions (each labelled):

- **Peak breach outflow** — use well-established **broad-crested weir + breach
  growth** relations (e.g. simplified **DAMBRK / NWS simplified dam-break**
  equations rather than reinventing). Parameters: breach width/depth/wall
  slope/formation time, plus storage-elevation curve.
- **Reservoir storage–elevation relationship** — from dam specs (source: real
  data) or an assumed prismatic wedge (source: assumption) if unavailable.
- **Breach formation time** — *highly uncertain*; default a range
  (minutes–hours) and **report the spread**, don't pick one magic number.
- **Inflow during breach** (rainfall) — **out of scope for V0.3** (added
  V0.4+); assume constant/small inflow or zero → state it.

Every breach parameter gets a **distribution / range** (`low`, `nominal`,
`high`) so we can produce a *banded* answer, satisfying “don't fabricate
precision.”

---

## 7. Reservoir outflow calculation

Produce the **outflow hydrograph Q(t)** at the dam:

1. Storage-elevation curve → starting volume from initial stage.
2. Breach option: weir equation across a growing breach:
   `Q ≈ C ·(breach geometry)·h**1.5` (broad-crested weir, `C ~1.6`), integrated
   as the reservoir empties (storage routing).
3. Release option: prescribed `Q(t)` (e.g. spillway/sluice schedule).

Output: `(t, Q)` pairs → the **inflow boundary** for the downstream model.

This is where the *assumption* of breach geometry dominates uncertainty, so the
hydrograph is produced **3× (low/nominal/high)**.

## 8. Downstream flood propagation model

The downstream reach from the dam to (and beyond) the plot is routed by a
hydraulic model. Two rungs, chosen by data availability and cost:

- **Hydrologic / simplified routing** (Muskingum-Cunge or a lumped
  attenuation) along the OSM `downstream_trace` path: fast, gives **peak
  attenuation, travel time, arrival-time estimate** at the plot for a given
  reach. Good first approximation, cheap, low data need.
- **Hydraulic 1D/2D run** (see §9): full depth/velocity.

Both consume the V0.2 `downstream_trace` path (`graph.downstream_trace`),
which enumerates the river edges from dam→plot with lengths. The trace
establishes **in-channel connectivity** (that a wave released at the dam can
reach the plot's river). Once the wave overtops, the **2D solver spreads it
across the floodplain on its own**, independent of the OSM graph (§3).

The key architectural seam: **the OSM trace seeds and connects the wave; the
terrain routes it.**

## 9. 1D vs 2D decision and why

**Recommendation: start 2D (a shallow-water, finite-volume model on a
regular grid) on the corridor DEM**, and use 1D concepts (analytic/weir routing
= §7), not a heavy 1D cross-section network, for the first pass.

Rationale:
- We want **depth + velocity + arrival time at an arbitrary coordinate**, which
  is naturally a 2D field. Reconstructing depth at an arbitrary point from a 1D
  network is fragile and needs quality cross-sections we don't have.
- Our input is a DEM grid — 2D raster methods map onto it directly.
- **CPU cost on a 10–30 m corridor is acceptable** for a single scenario (§18).

### HAND must NOT be an impermeable flood mask

This is a **hard architectural rule.** HAND (height-above-nearest-drainage) is an
**analysis product**, not a physical barrier.

- **Allowed uses of HAND:** computational-domain prior (skip clearly-unreachable
  mountaineous nodes), floodplain *initial screening*, prioritising where the
  solver looks first, sanity checking, and shrinking the raster we time-step.
- **Forbidden use:** treating the HAND corridor as a wall the solver cannot
  cross.

Why: a flood can cross relatively high HAND areas whenever the simulated water
surface reaches their elevation — water does not read HAND. The **hydraulic
solver decides reachability**, driven by:

```
terrain elevation + water surface + momentum + roughness + barriers + flow
```

So the pipeline is:

```
set HAND prior (domain reduction / screening only)
        ↓
run solver on (domain ∪ any cell the water surface physically reaches)
        ↓
plot floods iff solver says water reaches it
```

We keep the V0.2 principle “proximity ≠ connection” in a strict form: a cell is
only flooded by the solver, never by geometry/HAND alone — **and** the solver is
free to flood cells *outside* the HAND corridor when the water surface reaches
them.

We do **NOT** pretend to run a production HEC-RAS 2D static mesh here; instead
a lightweight structured-grid solver that reports **per-cell max depth, max
velocity, and time of peak** across the solver-decided wet domain. Same physics
as §10; simplified geometry (a single Manning value per land-cover class to
start).

### SA/DA python library
See §11 — we intend a Python-native shallow-water library (e.g.
`pysheds` for pre-processing + a NumPy explicit finite-volume shallow-water
solver), **not** a compiled proprietary engine, for the first version.

## 10. Hydraulic equations / model to use

Foundation physics (shallow-water equations, 2D conservative form):

- **Continuity:**  ∂h/∂t + ∇·(h u) = 0
- **Momentum (simplified: diffusion / kinematic wave for overland, or full
  shallow-water):**  ∂u/∂t + u·∇u = −g∇(h+zb) − g n² |u| u / h^(4/3)

Terms & parameters:
- `h` water depth, `u` depth-averaged velocity, `zb` bed elevation.
- **Manning's `n`** roughness per land cover (cells from OSM `landuse`
  later; a single calibrated `n` default this version). Vary `n` → but run
  nominal only; expose as sensitivity.
- **Weir / breach relation** (§7) supplies the upstream boundary.

We recognise: on a coarse 10–30 m grid with a single roughness, errors are
meaningful; hence outputs are **bands**, not points (§14).

## 11. Candidate open-source hydraulic engines/libraries

Libraries we should evaluate concretely (Python-first; pinned in
`apps/api/requirements.txt` style when chosen):

1. **pysheds** — flow direction/accumulation/watershed + HAND-style
   pre-processing on a DEM. Mature, small, NumPy-native. **Strong fit** for §2.
2. **xarray + rioxarray** — raster handling, warping, bbox I/O. **Strong fit**
   for DEM acquisition/management.
3. **NumPy / Numba** — the actual SWE finite-volume time-stepping loop.
   Numba JIT keeps it fast without C++.
4. **rasterio / pyproj / shapely** — read/write GeoTIFF, CRS transforms,
   geometry ops (already used for OSM traces).
5. **networkx** already available for any graph refinement (currently the graph
   is hand-rolled; we can keep that).

Considering but **not** committing yet:
- **HEC-RAS 2D** — gold-standard, but heavyweight, cross-section/geometry
  setup, needs a mesh, and is a CLI/binary integration rather than a Python
  library. Desirable later as a *validation cross-check*, not the V0.3 default.
- **ANUGA** (HydroPython) — 2D SWE finite-volume, Python-native, strong
  dam-break heritage. **A serious candidate** if the light solver proves too
  coarse; it handles wetting/drying and dry land well.
- **BASEMENT / TELEMAC** — too heavy for this project's scope.

Final recommendation: **pysheds + rasters for pre-processing, a small Numba
SWE solver (or ANUGA) for propagation, NumPy for storage routing.** Do not
couple V0.3 to a binary-only engine we can't inspect.

## 12. External engine (HEC-RAS) vs Python-native

**Decision: Python-native first; keep HEC-RAS as an optional validation
back-end.**

- Python-native (pysheds + SWE): inspectable, testable, license-clean,
  reproducible, fits our existing `DEM`/`DEM`+`numpy` stack, and works offline.
- HEC-RAS: use it **later** to *cross-validate* our depth/arrival numbers on
  the same Sutlej/Bhakra case, not as the primary simulator in V0.3.

We deliberately do not pretend HEC-RAS equals truth either — it is another
model. The *measured* (BBMB/CWC) flood-of-record data is the ultimate check
(§20).

## 13. Depth, velocity and arrival time at arbitrary coordinates

Every output is produced **at the plot coordinate** and reported as a range:

- **Arrival time:** from wave routing along the OSM trace (Muskingum/attenuation
  gives `t_arrival`; the 2D model refines it by “first flooded time” at the
  plot cell). Report `[low, nominal, high]` h.
- **Max depth:** max over time of `h` at the plot cell (2D) — or, in the
  1D-only fallback, depth from peak stage minus plot ground elevation
  (`max_stage − z_plot`), all labelled with confidence.
- **Max velocity:** max over time of `|u|` at the plot cell.
- **Peak discharge:** from the breach/storage routing hydrograph.
- **Inundation + duration:** the 2D solver's actual wet cells (whatever the
  water surface reached — **not** clipped to a HAND boundary), plus
  time-above-threshold per cell.

Because grid/depth estimates are coarse, values are always delivered with
**confidence and a range** (§14), never a false-precision float.

## 14. Representing uncertainty

Three explicit layers, surfaced in every report:

1. **Provenance tags** per input: `measured`, `derived-gis`, `assumption` — so
   a reader sees which numbers are facts (storage from BBMB) vs guesses (breach
   width).
2. **Parameter bands:** each key assumption carries `low/nominal/high`, and the
   sim runs the envelope (at least breach geometry + Manning). Output is a
   **range**, e.g. “depth 1.2–4.8 m (nominal 2.6 m)”, plus a qualitative
   `confidence: low/medium/high`.
3. **Methodology disclosure:** every output names the equations/software/dataset.
   If a required real DEM is unavailable, we **fall back to sample and mark the
   result `confidence=low / not-for-decision`**, matching V0.2's sample-DEM rule.

Nothing is ever presented as a single certain number at a decision-relevant
precision we don't actually have.

## 15. Measured data vs model assumptions — separation

This is enforced **structurally**, not just in prose:

- `data_provenance[]` already exists in V0.2 reports — V0.3 adds a
  `dam_characteristics[].source` and a `simulation.assumptions[]` list.
- Every number produced by a *model* is a **derived/simulated** field; every
  number observed is a **measured** field. The report clearly separates:
  - `measured`: real dam specs, observed flood-event data.
  - `derived`: flow direction, watershed, HAND, hydrograph, depth/velocity.
- Datasets with mixed licences remain listed separately (per `DATA_SOURCES.md` rule 3).

## 16. API / data-provider architecture

Add to the existing FastAPI app (`apps/api/routes`, prefix `/api`) in a

**New routes (read-only analysis endpoints):**
- `POST /api/v03/scenario` — submit `{lat, lon, dam_id|auto, breach/outflow
  scenario}` → runs the pipeline, returns a `scenario_id` + job status.
- (Async suggested in V0.3.1 because a 2D run is seconds–minutes.)
- `GET /api/v03/scenario/{id}` — result: bands for arrival/depth/velocity/peak,

- `GET /api/v03/dams` — the discovered candidate upstream dam records with
  their characteristics + source.
- (Deferred) `GET /api/v03/health`, raster tiles.

**Provider config (env, matching existing pattern):**
- `ELEVATION_PROVIDER` currently `sample` → V0.3 adds `copernicus`, `srtm`,

- `SIM_OUTPUT_DIR` → `simulations/outputs/` (dirs already exist).

The existing `upstream_trace`/`downstream_trace`/`network` endpoints are
**inputs** to V0.3 (they identify the dam and the downstream path); the
simulation endpoints are new and clearly versioned `v03`.

## 17. Cache strategy for DEM / hydrology

- **DEM tiles:** cache real DEM downloads (Copernicus/SRTM) by `(dataset, bbox,
  resolution)` in `data/cache/` (`CACHE_DIR` env already exists). Re-resample
  only when bbox/res changes; keep raw + derived rasters.
- **Derived raster products:** flow direction, flow accumulation, watershed,
  HAND — cache per DEM footprint so repeated analyses of the same corridor are
  fast.
- **OSM hydrology:** already fetched per call; add an optional TTL cache keyed by
  `(bbox, provider)` to cut Overpass load (mitigates the known 504/429 issue).
- **Simulation outputs:** cache by `(dam, scenario, corridor-bbox)`; never
  silently reuse a different-scenario result.

Cache invalidation: `(dataset, bbox, resolution)` composite key; re-fetch on
provider/version bump.

## 18. Computational requirements (local)

**The hydraulic domain is determined dynamically, not assumed.** For a small
local flood a small corridor is fine; for the actual “Bhakra fails” question the
domain must extend far enough downstream (see §I). The corridor is the solver's
*active* wet/at-risk region, decided from:
source (dam) → traced channel → plausible floodplain extent → plot.

Cost scaling (JIT/Numba, single scenario):

- **Pre-processing** (resample, flow dir, accumulation, watershed, HAND on a
  small–medium corridor): seconds to ~1 min — trivial with NumPy/Numba.
- **Hydrologic routing** (Muskingum along `downstream_trace`): milliseconds.
- **2D SWE burst:** tens of seconds to a few minutes per scenario on a laptop
  for a modest grid; **scales linearly with cell count**, so a long
  multi-km Bhakra→Ropar reach at a coarse grid is feasible, and a fine grid is
  not — the trade-off is made explicit and reported.
- When the domain is large or many scenarios are wanted, we **(a)** reduce
  `simulation_grid`, **(b)** restrict the solver's active region with HAND only
  as a *performance* prior (never a hard mask), or **(c)** run scenarios
  offline in `simulations/outputs/`.

Conclusion: **feasible locally** for V0.3's single-scenario analysis, with cost
proportional to the real hydraulic domain — and Phase 0 measures the *actual*
Bhakra→Ropar domain size before we commit to a solver grid (§I).

## 19. Test strategy

Extend the existing `tests/` structure; keep all 48 V0.2 tests green
(no behavior change to V0.2).

**Golden / synthetic tests (fast, deterministic):**
- Breach hydrograph shape: weir/storage-routing against hand-computed values.
- Muskingum-Cunge attenuation on a known synthetic reach → known peak/time.
- SWE solver on a synthetic 1D channel: depth/velocity match analytic
  (e.g. dam-break on a dry-frictionless channel, Ritter solution regime).
- **Solver, not HAND, decides reachability:** a cell outside the HAND corridor
  must flood when the water surface reaches it (HAND is a prior, not a wall);
  and a visibly *disconnected* basin (no hydraulic path) must **not** flood —
  mirrors the V0.2 “proximity ≠ connection” principle.

**Property / regression tests:**
- monotonic non-arrival-time-worsening as distance grows; outputs bounded
  (depth ∈ [0, plausible_max], velocity ≥ 0).
- determinism: same input → identical output across runs (we harden the
  non-determinism discipline from V0.2).

**Fixture tests:** use synthetic DEM/synthetic dam records; never network.

### 20. Validation using a real Punjab/Sutlej case

**Validation ≠ guessing.** We must not hard-code any single event (e.g. “the
1966 flood”) as “the truth” before it is documented. The plan is event-driven:

1. **Build a historical-event dataset from authoritative records first** —
   gather candidate dam-releases/breaches/floods from **CWC and India-WRIS
   records and BBMB (Bhakra–Beas Management Board) operational/release data**,
   plus established gauge observations along the Sutlej (Ropar, Ludhiana,
   Phillaur). CWC is a documented authority that performs flood-routing studies
   for Bhakra/Pong from BBMB data; that is the kind of primary material to use.
2. **Select the validation event** from that dataset only after the event's
   peak discharge, peak stage, timing and inundation evidence are *verified*
   against the records — not from an assumption. (If 1966 turns out to be
   well-documented, it may be selected — but only as a *selected instance*,
   with its evidence shown.)
3. **Model the same scenario** with real (Copernicus/SRTM) DEM + real dam
   specs from BBMB + a documented breach/release scenario.
4. **Compare at gauge sites:** predicted peak stage / arrival time vs observed.
   Report error, not ignore it. Acceptable if within the uncertainty band we
   declared; if not, tighten assumptions.
5. **Sensitivity:** vary breach width/Manning/stage; show which dominates.
6. **Honest residual:** publish the gap between model and measurement.

**Success criterion for V0.3:** for the selected Sutlej event, our depth/arrival
bands *contain* the observed values at the gauge sites. If we can't achieve
containment, we say so and widen/annotate rather than force-fit.

## B. The channel / bathymetry problem (the hardest DEM limitation)

A 30 m satellite **DSM** does not see the underwater riverbed, nor most
engineered structures. For the flood question this matters enormously, and we
must be explicit about it rather than pretend “burning the OSM river into the
DEM” fixes it.

What a 30 m DSM is **poor at** representing:

- **river bathymetry** — the actual submerged cross-section / thalweg depth
- **embankments / bunds** — narrow linear features that a flood model depends on
- **small channels, culverts, bridges, drainage structures** — the very things
  that control how a flood escapes the channel

Consequences & policy:

- **OSM river geometry is a *path/routing aid, not bathymetry.*** Burning the
  OSM channel into the DEM fixes where the thalweg is, but **not** its true
  depth/shape. We must not claim a real cross-section from it.
- Where the reach is engineering-critical (Bhakra toe, Ropar), we either
  (a) use a synthetic-but-labelled channel assumption and widen uncertainty, or
  (b) if a project-grade survey/bathymetry is obtained, mark it `measured` and
  use it. Until then, channel conveyance is an **assumption**, not a fact.
- **Phase 0 explicitly documents** how well/poorly the real 30 m DEM represents
  the Sutlej channel and any identified embankments/bridges on the Bhakra→Ropar
  reach, before we commit to a solver (§I).

## J. Phase 1 — hydraulic/domain design specification (design-first, NO solver yet)

### J.0 Orientation

Phase 0 (completed, `REAL DEM: SUCCESS`) proved the *pipeline* works: real GLO-30
terrain for the Bhakra→Ropar corridor is fetched → preprocessed → domain
quantified (2,318,040 cells at 30 m over ~1,962 km²) → provenance preserved.
That is **not** the same as proving the *hydraulic model* is ready for a
property-level conclusion.

The real goal is not *“can we run a solver?”*; it is:

> **“Can we produce a physically credible, evidence-grounded flood-risk
> assessment for the actual property (plot + building)?”**

Therefore Phase 1 is specified as a **design + constraining-observations
contract first**, and only after that contract is agreed do we write any
solver/propagation code.

Phase 0's empirical findings that shape this design:

1. The Ropar plot cell is **flat** (267.5 m, all 8 neighbours identical):
   D8 direction undefined, HAND `NaN`, accumulation=1, DEM drainage = 0 km.
   The bare 30 m DEM cell cannot establish drainage connectivity on its own.
2. OSM **upstream** reach works (743 nodes); OSM **downstream** reach is not
   reliably attachable at the plot (“Plot could not be attached to a river
   network node”).
3. Datum is EGM2008; dam/gauge absolute elevations come from other sources and
   are **not reconciled** → every absolute-elevation comparison is
   `confidence=low` until resolved.
4. 30 m GLO-30 cannot resolve local flood-control infrastructure (small
   channels, drains, culverts, road/rail embankments, small bridges, field
   bunds, local grading, walls, small depressions).

### J.1 The no-fabricated-path principle (non-negotiable)

The system **must never manufacture a drainage/flood path merely because the
DEM cannot resolve one.** Connectivity and flood depth are *evidence-constrained*.

- If the evidence is insufficient to establish connectivity from the channel to
  the plot, the result is a first-class, explicit output:

  > **“Hydraulic connectivity unresolved at 30 m DEM resolution.”**
  > *(and, where applicable, “at the available evidence resolution.”)*

- This is a **valid outcome**, not a failure. It is never silently replaced by
  a fabricated “low risk” or a fake flood-depth number.
- Every depth/extent/connectivity conclusion carries an explicit
  `confidence` and the list of evidence that supports it.

### J.2 The runnable pipeline (Phase 1 target architecture)

```
Real DEM (GLO-30)              ── Phase 0 ✓
   │  pit-fill / D8 / accum / HAND (prior only)
DEM pre-processing
   │
Sutlej / channel network (OSM centreline + drains + infra)
   │
Plot location (property + building)
   │
Hydrologically connected terrain domain
   │  -- connectivity is EVIDENCE-BASED (J.1), not fabricated
Flood propagation / 2D hydraulic model   (NOT in Ph1 spec, see J.7)
   │
Water depth + extent at plot
   │
House/building elevation
   │
Risk assessment (property hazard)
```

Each arrow is a phase gate; the propagation + depth + building-elevation +
risk stages are **not** implemented in the Phase 1 *design* deliverable — the
design specifies their *requirements and constraints* so that later
implementation is not assumption-driven.

### J.3 Constraining-observations contract (what evidence is allowed)

Before any flood depth is produced, the model binds to an explicit set of
external observations. Phase 1 must declare which of these are available,
authoritative, and fit-for-purpose for each step. None of these may be silently
assumed:

| Evidence | Purpose | Status needed before use |
|---|---|---|
| Sutlej centreline (OSM way) | channel path / anchoring geometry | present, id `919730633` verified |
| Known channels / drains | micro-drainage connectivity | inventory against OSM `waterway` + local data |
| Road / rail embankments | flood escape blockers | whether present in DEM / OSM / local maps |
| Bridge / culvert locations | conveyance + blocking | whether present and their effective gaps |
| Gauge observations (CWC / India-WRIS / BBMB) | water-surface / stage calibration | datum reconciled vs EGM2008 → else `low` |
| Documented flood extents | calibration / validation | event-based, not hard-coded (see §~/H) |
| Local survey / ground elevations | property + micro-topography | measured, `measured` tag, high trust |
| High-resolution DEM around plot (final step) | property-level answer | < 30 m (e.g. drone / LiDAR / survey) |

**Rule:** a conclusion is only as strong as its weakest allowed evidence. A
plot-level answer (building-scale) **cannot** be considered credible on GLO-30
alone; it requires the high-resolution/local-survey row. Without it, output is
the J.1 “unresolved” statement, not a number.

### J.4 Domain & connectivity rules (Phase 1 implementation gates)

Do **not** build this layer until the constraint contract (J.3) is agreed — that
is the whole point of design-first. When implemented, it must:

1. **Anchor to the Sutlej centreline**, not the bare plot cell. Connectivity is
   evaluated channel → floodplain → local drainage → plot → building, with each
   hop evidenced.
2. **Define “valid connectivity” explicitly** before computing it: a connection
   exists only if there is a supported physical path (terrain gradient / water
   surface / hydraulic structure) backed by evidence at an adequate resolution.
   Absence of a resolvable path = unresolved (J.1), never an assumed barrier or
   an assumed open channel.
3. **Keep HAND as a prior only** (never an impermeable boundary, never “flood
   depth”). Solver decides reachability with water surface + momentum +
   roughness + barriers + flow.
4. **Embrace the dynamic domain** from Phase 0 (~2.3 M cells at 30 m); do not
   fall back to a hard-coded 10×10 km box.

### J.5 Datum & provenance convergence

- Carry the EGM2008 datum and source/sim resolution through every stage
  (Phase 0 already does).
- Before any absolute-elevation comparison, reconcile dam/gauge datum vs EGM2008;
  until reconciled, all such comparisons are `confidence=low`.
- Never silently mix EGM2008 and EGM96, never silently fall from GLO-30 to SRTM
  (record provider, reason, source URL, product, native res, CRS, datum, ops).

### J.6 Known failure modes / limitations Phase 1 must respect

1. Flat floodplain → D8/HAND degenerate at plot (cannot infer routing).
2. OSM downstream reach not attachable at the plot point.
3. 30 m DSM blind to bathymetry, embankments, bridges, culverts, drains.
4. Datum offset unresolved until gauge/survey tied to EGM2008.
5. Risk of “beautiful-looking flood maps whose precision exceeds the evidence” —
   guarded by J.1 + J.3.

### J.7 Explicitly out of scope for THIS design deliverable

- Breach/outflow hydrograph, Muskingum routing, 2D SWE solver, flood propagation,
  model calibration runs — **all deferred**. The design is the deliverable.
- No solver/connected-domain code. Phase 0 is unchanged. No V0.2 changes.

### J.8 Phase 1 acceptance (design deliverable)

- Constraining-observations contract (J.3) explicitly lists what data is
  required for a credible plot-level conclusion, and which rows are missing.
- No-fabricated-path rule (J.1) is encoded as an output contract.
- Domain/connectivity rules (J.4) are specified before any code.
- Datum/provenance convergence (J.5) and failure modes (J.6) are documented.
- Pipeline order (J.2) is explicit: network → connected domain → propagation →
  plot depth → building elevation → risk, with propagation+risk NOT implemented
  in this deliverable.
- Phase 0 remains unchanged; 48/48 V0.2 tests still pass.

**Stop here for review.** Do not implement the solver or the connected-domain
layer until this design is approved.
